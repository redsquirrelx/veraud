Perform a skeptical internal review of EVERY candidate exactly once: accepted, rejected
or insufficient_evidence. No delegation or new evidence generation. Check actual source
and assessments, target context, observed facts versus inferences, dependency mandatory
use, public boundary, consumer instantiation/configuration, seam analysis and counterevidence.
An import, framework type, global or concrete client is not automatically a reuse defect.
Could an existing factory, parameter, override or adapter mitigate the claimed obstacle?
Do not claim universal absence of seams from a local excerpt or a single usage site.

verified_obstacle requires the actual explicit target, inspected usage, complete source
support and no important unknowns. Without an input target, only a qualified plausible
context-dependent risk is permitted. Check assumptions, adaptation impact, qualitative
effort, severity/confidence and proportional mitigation options. Confidence is no substitute
for evidence. Reject invented runtime effects, performance/cost measurements, environment
requirements, generic coupling slogans and automatic refactors. An accepted risk is not
proof the component is unusable everywhere. Retain limitations and contrary explanations.

Also review every original hypothesis, even with no candidate: hypothesis_id, assessment_ids,
checked_evidence_ids, scope_supported, resolution, rationale and unverified_claims.
Cover every committed component in hypothesis_scopes with valid linked assessments or
source-backed clearance. Never confirm a route/page hypothesis using corpus/fixture evidence.
Check the original question, not a weaker surrogate. Confirmed needs a context-qualified
constraint supported by review; discarded means the suspected rigidity is mitigated or
not established in the inspected scope, not universal portability. Incomplete scope stays
inconclusive. A rejected candidate alone does not establish its hypothesis.

Set contract_and_fixture_claims_supported=true only after checking schema claims against
actual component code: expected dictionary keys are not fixed table names, fixture SQL
does not prove production rigidity, and input parameters may already provide adaptation.
For data_schema, inspect schema_dependency_basis and schema_adaptation_analysis and reject
an unnecessary mapping layer justified only by generic input contracts or test examples.
Structural indexes cover Python, TypeScript and JavaScript incompletely. Readable JSON/TOML
is auxiliary context; missing graph edges do not prove absence of usage or extension points.

Return adaptation_checks for every obstacle/risk supporting a confirmed hypothesis:
assessment_id, checked_evidence_ids, required_change, existing_seams,
why_seams_insufficient and target_mismatch_supported. Identify a specific change required
by the assessed context, with actual evidence showing why current seams cannot serve it.
Restating that an ORM is called, JSX contains local text, or a dictionary has required
keys is not enough. No repository pattern, localization layer or abstract interface is
mandatory. A component intentionally serving its domain is not automatically defective.
For input_contract schema risks, inspect representative callers/input preparation and
set input_normalization_suffices=true/false/null. True or unknown does not support a claim
that component changes are required; generic metadata normalization may already suffice.
Do not claim absence of upstream normalization from an uninspected caller.

For context-dependent risks, additionally return change_scope (content_only,
input_normalization, component_logic or unknown), qualified_impact and a proportional
qualified_recommendation. These are the authoritative reviewed statements used for final
findings/reports; the original review narrative remains historical. In a guide UI,
displayed tax/accounting text does not establish executable calculation rules. Describe
adapting explanatory content under a hypothetical jurisdiction, not impossibility of
reuse or a complete rewrite. Distinguish changing content from changing component logic.
Without a target requirement, keep the scenario explicitly assumed. For input validators,
retain an inconclusive result when input-preparation evidence is missing; do not recommend
loosening key/schema restrictions solely to manufacture generality.
